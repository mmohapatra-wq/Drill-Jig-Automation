The drill-jig code is version-sensitive to widget names and API quirks. 3 · Register the Creo VB API COM objects

Every tool connects through the pfcls COM automation objects. They must be registered once (per machine / per Creo install), as Administrator.

# Run PowerShell/cmd as Administrator. Path is your Creo install's Parametric\bin.
cd "C:\PTC\Creo 12.4.3.0\Parametric\bin"
.\vb_api_register.bat
Self-healing fallback
Every drill-jig tool also attempts registration automatically on first run: if New-Object -ComObject pfcls.pfcAsyncConnection throws, the tool shells out to vb_api_register.bat under the running Creo's install path. So the manual step above is mainly for a clean machine or after a Creo upgrade.

How the connection works (the shared header in every tool)

# Creo must already be running with a model open. Tools find it by the xtop.exe process.
$proc = Get-Process -Name xtop
$Env:PRO_DIRECTORY    = $proc.Path.TrimEnd("xtop.exe")
$Env:PRO_COMM_MSG_EXE = $proc.Path -replace "xtop.exe","pro_comm_msg.exe"
$async      = New-Object -ComObject pfcls.pfcAsyncConnection
$connection = $async.Connect($null,$null,$null,$null)
$session    = $connection.Session
$model      = $session.GetActiveModel()
One Creo, part mode
Tools expect exactly one xtop.exe and (for geometry creation) the jig part open — not an .asm. Assembly mode resolves selections against the assembly, not the part being drilled.

9 · BlueGPT judge / blind-evaluator convergence layer

The toolkit ships a blind evaluator (lib\blind_evaluator.ps1) — it derives a claim, measures ground-truth geometry into a "slice," and asks an LLM judge to confirm/refute without seeing how the claim was produced. There's also a response-convergence harness that turns the same idea on Claude's own edits. Both call a BlueGPT LLM over an OpenAI-compatible endpoint.

How the judge config resolves (first match wins)

  1. .bluegpt_judge.json at the repo root — { "base": ..., "token": ..., "model": ... }. Gitignored (it's a secret). Optional override.
  2. ANTHROPIC_BASE_URL + ANTHROPIC_AUTH_TOKEN — already set by Claude Code on this machine (they point at https://litellm.leap.blueorigin.com). This is the path in use — no extra setup needed.
  3. BLUEGPT_API_BASE + BLUEGPT_API_KEY — explicit override env vars.
Zero-config by design
Because Claude Code already exports the ANTHROPIC_* variables, the judge works out of the box. If none resolve, the evaluator still writes its packet and simply skips the network call — it degrades to offline, never fails a run.

Transport & validation

LiteLLM-fronted, OpenAI-compatible: POST {base}/v1/chat/completions, Authorization: Bearer <token>, response_format = json_schema (strict). Validate the round-trip in isolation with the probe flag (sends a synthetic true+false packet, expects confirm+refute):

.\plane-probe.cmd --probe-judge
Secrets stay out of git
.gitignore excludes .bluegpt_judge.json and all *_eval.json packets. Never commit tokens.

10 · Efficient querying — the whole point of vb-docs

The governing rule from CLAUDE.md: when writing or debugging VB API code, consult the vb-docs MCP server to verify method signatures, parameters, and return types before relying on memory.

Query modes

mode=function — exact name lookup, O(1). Use for IpfcSession, RunMacro, CMpfcSelect, EpfcModelType.

mode=semantic — natural language. Use for "how to create a feature", "offset a datum plane".

mode=auto (default) — detects which. Start here.

Keep it cheap

Query narrow (one symbol / one concept), take the top hit, keep limit small (default 5). The index is sub-millisecond — many small queries beat one broad one.

For a class factory (CMpfc* / CCpfc*) confirm the real ProgID — those names are a known gotcha (never standalone ProgIDs).

Auto-approve the query tool (no prompts)

Add the tool to the project's allow-list so every lookup runs without interruption. In .claude\settings.local.json of the drill-jig repo (already set here):

{
  "permissions": {
    "allow": [ "mcp__vb-docs__query_vb_api_docs" ]
  }
}

The confirmed-facts registry — don't re-litigate what's known

Live-verified and refuted API facts are recorded in lib\creo_api_facts.json (queryable via lib\creo_api_facts.ps1 by id / symbol / category / status). Check it before trusting a remembered behavior — e.g. "plane normals read null on this build", "IpfcPoint.Point crashes", "the pfcls.pfcRegenInstructions ProgID (not CC*)".

11 · The F8 interactive development loop

The fastest way to discover live API behavior (from GETTING_STARTED.md):

  1. Open a .ps1 file in VS Code; start Creo with a model open.
  2. Ask Claude for a snippet ("give me connection code"), then select the lines and press F8 — the PowerShell extension runs the selection in the integrated terminal against the live Creo session.
  3. Explore any COM object: $model | Get-Member.
  4. Iterate: Write → F8 → Observe → Ask Claude → repeat. Paste any error back for a docs-grounded fix.
Mine trails, don't guess widgets
Mapkey widget names come from recording real Creo interactions (visible_mapkeys yes in config.pro) and reading working_folder\trail.txt.N — the probe/recorder tools (*-probe.cmd) exist to capture exact tokens. This is the mine-don't-guess rule the codebase enforces.

13 · Safety rules

Never auto-run these against a live model without explicit intent
  • $model.Regenerate($null) — can corrupt a half-committed model
  • $model.Save() — permanent modification
  • Trail commands prefixed with <, @, ** — view-dependent / unsafe to replay
  • ID-only, never coordinates. Foreign/imported bodies aren't API-traversable and IpfcPoint.Point crashes — select by ID; let the human judge geometry visually.
  • Atomic RunMacro. A dashboard's command context does not survive across RunMacro calls — fire open→set→confirm as one string.
  • Honest verification. "Done" means the model actually changed (VersionStamp canary) or geometry was measured — never "the macro fired."
  • Close modal dialogs in Creo (Parameters, Relations, Find) before an API call, or it can hang.
